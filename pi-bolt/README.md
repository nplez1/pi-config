# pi-bolt

[Pi-Bolt](https://pi-bolt.opensec.in/) — the Pi coding agent compiled ahead of time
to native code — set up for this pi-config: the three prebuilt bundles that keep the
local forks fast, the `pi` → pi-bolt swap, and the compile exclusions.

All of it is provisioned by `pi-config/install.sh`: it installs Pi-Bolt if it is
missing, materializes the package list, rebuilds whatever bundle is stale, compiles
the installed extensions into the executable (everything except
`pi-bolt/compile-exclude.txt`), pins a patched `undici` in the extensions project,
and swaps `pi` to run pi-bolt. Revert the swap with `pi-bolt/pi-swap.sh remove`.

Everything here is shared; the build output is not. `build-info.json` and `dist-bun/`
are generated by each machine's first rebuild, and `.pi-swap-state` records what
`~/.local/bin/pi` pointed at before the swap. Pi-Bolt's package overrides live in the
seeded `~/.pi/agent/settings.json` under `piBolt`, which stock `pi` ignores.

## The build variant: JIT on

`pi-bolt` ships two builds per platform and the installer defaults to the JIT-less
one. This machine runs the `-jit` variant (`PIBOLT_VARIANT=arm64-jit`) as of
2026-10-19, which also retires the `bun:ffi` warnings `doctor` printed for
`opensec-pi-fff` and the web-access bundle (that hint only fires when the JIT is
off — see [Pi-Bolt#62](https://github.com/opensec-git/Pi-Bolt/issues/62)).

Measured on this machine before switching, both builds sharing `~/.pi/agent` and
the same 14 extensions, alternating runs:

| | JIT off | JIT on |
|---|---|---|
| idle TUI (one open session) | 184.2 / 183.3 MB | 188.7 / 188.5 MB |
| short session (one `-p` turn) | 213.2 MB | 218.9 MB |
| `doctor` (all extensions loaded) | 104.8 MB | 110.9 MB |
| `--version`, nothing loaded | 27.9 MB | 25.6 MB |
| `doctor` CPU time | 0.22 s | 0.22 s |
| cold start, `TOTAL` (jiti cache cleared) | ~376 ms | 500–622 ms |
| warm start, `TOTAL` | ~56 ms | 56–84 ms (median ~61) |

So the JIT costs ~5 MB per session (2–3%), ~200 ms on the first start after the
jiti cache is cleared, and bought no measurable CPU time on this workload mix:
extension loading is bound by jiti's TypeScript transform and file IO, and tool
work is bound by the model call. The reason to run it is not speed — it is that
`bun:ffi`'s `dlopen` then works, which was `opensec-pi-fff`'s primary backend
(it also served the web-access bundle), and `doctor` stops advertising a
requirement that isn't one. `opensec-pi-fff` was dropped from the package list on
2026-10-22, so the web-access bundle is the remaining reason to keep the variant.

`pi-bolt update` preserves the variant (it passes `PIBOLT_VARIANT` from the
running build); the raw installer does not, so `install.sh` passes it explicitly
and migrates an existing non-JIT install.

The old `pi-bolt-darwin-arm64` and `pi-bolt-darwin-arm64.previous` folders (~426 MB
together) are inert leftovers of the JIT-less install. `pi-bolt update --rollback`
only ever touches `pi-bolt-<platform>-<variant>.previous`, so deleting them is safe
once the JIT build has been used for a while.

## What pi-bolt loads differently from pi

`~/.pi/agent/settings.json` → `piBolt.packages` (an overlay on the shared
`packages` list; `pi` never reads it):

```json
{
  "packages": [
    "npm:opensec-pi-todo@2.13.1",
    "-plugins/pi-todo",
    "-plugins/pi-subagents",
    "pi-bolt-bundles/pi-bolt-subagents",
    "pi-bolt-bundles/pi-bolt-web-access",
    "-npm:pi-web-access",
    "-plugins/pi-advisor-subagent",
    "pi-bolt-bundles/pi-bolt-advisor-subagent"
  ],
  "packagesOverlay": true
}
```

So under Pi-Bolt: OpenSec's bun prebuilts replace the local todo fork, and the three
bundles built here replace the local subagents and advisor forks and npm's
pi-web-access. Stock `pi` still loads `plugins/pi-todo`, `plugins/pi-subagents`,
`plugins/pi-advisor-subagent` and `npm:pi-web-access` untouched.

## Results

`PI_TIMING=1 <cli> -p "x"`, `TOTAL` of the main phase. Cold = `~/.pi/agent/cache/jiti`
removed (that cache is Pi-Bolt's alone; `pi` uses Node's `enableCompileCache()` and
has no such cold penalty).

| | original | now | `pi` for reference |
|---|---:|---:|---:|
| cold | ~2520 ms | **~376 ms** | ~392 ms |
| warm | ~214 ms | **~56 ms** | ~370 ms |
| `--version` | 10 ms | 10 ms | 120 ms |

Cold used to be Pi-Bolt's worst case (2.5 s against `pi`'s 0.38 s, because jiti
transpiles every TypeScript extension when its cache is empty and `pi` has Node's
compile cache instead). It is now *faster* than `pi`.

Every figure in this section was measured on the JIT-less build, which is what the
bundles were built for. On the `-jit` build (see "The build variant") the warm
number is unchanged — 56, 61, 84 ms for `TOTAL` warm, so ~61 ms median — but **cold
start is slower: 622, 617, 500 ms** against the ~376 ms above, i.e. ~200 ms of JIT
warmup that the AOT-compiled build does not pay. That is the one place the JIT-less
build is genuinely faster, and it is a first-launch-per-cache cost, not a per-turn
one.

| `pi-web-access` | 958 ms | **12 ms** |
| `plugins/pi-subagents` | 807 ms | **9 ms** |
| `pi-codex-goal` | 216 ms | 0–5 ms (compiled in) |
| `plugins/pi-advisor-subagent` | 145 ms | **2–6 ms** |

What is left is spread thin: `pi-web-access` 12 ms, `orca-prefill` 8 ms,

### Why the advisor plugin cost 41 ms for 114 KB

It looked disproportionate, so it was measured rather than assumed. The cost is per
**module**, not per byte:

| extension | modules | size | warm, Pi-Bolt | warm, `pi` |
|---|---:|---:|---:|---:|
| `extensions/orca-agent-status.ts` | **1** | **62 KB** | **0 ms** | 1 ms |
| `extensions/model-manager.ts` | 1 | 14 KB | 0 ms | 2 ms |
| `plugins/pi-advisor-subagent` | **22** | 114 KB | **41 ms** | 64 ms |
| `plugins/pi-todo` (as TS) | 17 | 75 KB | — | 33 ms |
| `plugins/pi-subagents` (as TS) | 65 | 1048 KB | — | 189 ms |

A 62 KB *single* module is free; 114 KB across 22 modules is 41 ms — about 1.8 ms
per module, the same model on Node (≈2 ms). Each module pays a jiti cache read, a
wrapper eval in the bytecode interpreter (these were measured on the JIT-less
build, which is where the interpreter matters), and an
async `jitiImport(...)` for every bare import — that plugin's graph has ~42 of them.
jiti's raw transform of those 25 files measures 2.9 ms/file, so the transpile alone
would be 72 ms with the cache cold; warm loads trade that for per-module overhead.

Two other things fall out of this and were worth knowing:

- **It was never a Pi-Bolt problem.** Node took 64 ms for the same extension.
- **It is why bundling works so well.** Collapsing 22 modules into 1 and removing
  jiti is the whole fix, which is also why the 1048 KB subagents source loads in
  7 ms as a bundle and 189 ms as TypeScript.

## The three bundles

Both are the same trick, which is what OpenSec's own `dist-bun/` packages do: Pi
evaluates an extension's entry through jiti, which transcribes TypeScript/ESM on
every cold start. So the entry is kept tiny and the real work goes into a single
CommonJS file that Bun `require`s natively, never through jiti.

```
pi-bolt/   (this directory; `~/.pi/agent/pi-bolt-bundles` -> it)
  lib/bundle-info.mjs         the fingerprint + build-info writer + shim snippet
  rebuild.sh / rebuild.mjs    the pre-launch check and rebuild driver

  pi-bolt-subagents/          pi-bolt-web-access/       pi-bolt-advisor-subagent/
    package.json                package.json              package.json
    build-info.json             build-info.json           build-info.json
    scripts/build.mjs           scripts/build.mjs         scripts/build.mjs
    dist-bun/index.js           dist-bun/index.js         dist-bun/index.js   the jiti shim
    dist-bun/core.cjs           dist-bun/core.cjs         dist-bun/core.cjs   the extension, as CJS
                                node_modules -> ~/.pi/agent/npm/node_modules
```

`core.cjs` cannot `require` Pi's modules directly — it loads outside jiti's module
graph, where Pi's aliases do not resolve — so the builders rewrite the host imports
(`@earendil-works/pi-coding-agent`, `.../pi-ai`, `.../pi-tui`, `typebox`,
`@sinclair/typebox`, plus any subpath such as `.../pi-ai/compat`) to a lookup on a
global that the shim populates.

Rebuild after the source changes (or let the hook do it):

```sh
~/Code/pi-config/pi-bolt/rebuild.sh            # all three, whatever is stale
~/Code/pi-config/pi-bolt/rebuild.sh --force    # all three, unconditionally
```

Each builder also runs on its own (`bun <bundle>/scripts/build.mjs`). They read
their source and never write to it. Restart Pi-Bolt afterwards.

### Wiring

| | host modules | dependencies |
|---|---|---|
| subagents | `pi-coding-agent`, `pi-tui`, `@sinclair/typebox`, `typebox/value` | `croner`, `nanoid` — inlined |
| web-access | `pi-coding-agent`, `pi-ai`, `pi-ai/compat`, `pi-tui`, `typebox` | 9 runtime deps — left external, via the `node_modules` symlink |
| advisor | `pi-coding-agent`, `pi-ai`, `pi-tui`, `typebox`, `typebox/value` | `@juicesharp/rpiv-config` — inlined, so no symlink needed |

### What the advisor needed that the other two did not

**A module that reads assets relative to its own URL.** `advisor/prompt.ts` loads
`../prompts/<name>` from `import.meta.url`, at module init:

```ts
export const ADVISOR_SYSTEM_PROMPT = load("advisor-system.txt");
```

so it throws on load rather than degrading if the base is wrong — and `import.meta`
is invalid in CommonJS anyway. The builder replaces each module's `import.meta.url`
with that module's own original file URL, which keeps the prompts resolving to the
live `plugins/pi-advisor-subagent/prompts/`. **Prompt edits therefore take effect
with no rebuild**, which is also why `prompts/` and `agents/` are excluded from the
staleness fingerprint: they are not in the bundle, so they cannot make it stale.

**Host detection had to change.** The web-access builder pre-scanned its entry
file, which works because that entry is one already-bundled file. Doing the same
here found **one** of the four host packages — the imports are spread across 22
modules plus an inlined dependency — which would have bundled duplicate copies of
Pi. The advisor builder instead collects host specifiers as bun resolves them
during the build, and asserts afterwards that no `require("@earendil-works/...")`
survived into the output.

### Two problems worth remembering

**Inlining pi-web-access' dependencies was wrong.** The first attempt produced a
6.8 MB bundle from a 1 MB source and would not load: two inlined dependencies use
`import.meta` — `import.meta.resolve("pdfjs-dist/package.json")` in unpdf — and
`import.meta` is not valid in CommonJS. Rewriting a third party's `import.meta`
correctly is guesswork, so the deps are left external, exactly as the published
bundle had them, and resolved at run time from the same hoisted copy Pi uses. That
needs `node_modules` beside the package; the builder creates it as a symlink to
`~/.pi/agent/npm/node_modules`. The bundle is 1063 KB against a 1046 KB source.

**Bun's CJS/ESM interop breaks default imports of ESM externals.** Bun emits
`__toESM(require("p-limit"), 1)` for a default import of an external module, and
its `__toESM` is:

```js
const to = isNodeMode || !mod || !mod.__esModule || !__hasOwnProp.call(mod, "default")
  ? __defProp(target, "default", { value: mod, enumerable: true })
  : target;
```

That flag makes the first branch unconditional, so `default` is bound to the whole
namespace — and because `to` now already owns `default`, the module's real default
export is never copied over it. At run time: `import_p_limit.default is not a
function`, which broke every fetch and search. The builder drops the `, 1`.
Dropping it is a no-op for CJS externals (`!mod.__esModule` still takes the
branch) and a fix for ESM ones, so it is the right change for both, and the build
asserts how many call sites it rewrote so it cannot silently stop applying.

## Staying fresh (automation)

A bundle is a snapshot, and nothing about it notices when its source moves on. The
failure is silent — pi-bolt just keeps running old code — so one record feeds two
checks, and **nothing runs per launch**.

| Piece | Role |
|---|---|
| `lib/bundle-info.mjs` | the fingerprint, the `build-info.json` writer, and the snippet the builders inline into their shims |
| `<bundle>/build-info.json` | what this build was made from: inputs, source version, fingerprint, rebuild command |
| `rebuild.sh` / `rebuild.mjs` | the driver: `--if-stale` (default), `--check`, `--force`, `--verbose` |
| the `pi` shim (`pi-swap.sh`) | runs the driver after `pi update` — the one command that changes a bundle's source in normal use. Every shell, not just an interactive one |
| the generated bundle shim | checks itself in-process on load (~0 ms, no process spawn) and warns when something got past the hook |

```sh
rebuild.sh              # rebuild whatever is stale
rebuild.sh --check      # report and exit 1 if stale; rebuild nothing
rebuild.sh --force      # rebuild all three regardless
```

**"Stale" means** the fingerprint moved (file count, total bytes, newest mtime) or
the source's `package.json` version differs from the recorded one. The version is
not redundant: an mtime walk cannot see a source that changed to *older* content —
a `git checkout` of an earlier revision, a downgrade — and the version catches
that outright. A missing `build-info.json` counts as stale, because rebuilding once
is cheap and trusting a bundle of unknown provenance is not.

### Why nothing is checked per launch

An earlier version rebuilt before every pi-bolt launch. It cost **14.5 ms** — almost
all of it process start-up, since the fingerprint walk itself measures ~0 ms — and
on what was then an ~85 ms warm start that is ~17%, which is not worth paying to
catch a case the hook already catches.

That trade only holds because of two things about how this machine is actually
used: `pi update` / `pi update --extensions` is the only route by which a bundle's
source changes in normal use, and an agent that edits a plugin or adds one is
expected to rebuild as part of that work. Both caveats are real, and they are why
the shim's in-process check stays:

- **`pi update` does not cover the subagents fork.** That comes from a git
  submodule, so `git submodule update` or re-running
  `~/Code/pi-config/install.sh` moves it with no hook involved.
- **`pi-bolt update` and `pi-real update` are not hooked**, though the bundle
  shim catches the first next start, and `after-update.sh` exists for both.

The shim check costs nothing measurable — both bundles still load in 5–9 ms, the
same as before it was added — so it is the cheap half of the earlier design, kept
for exactly those three routes.

### Working on a plugin (agent or human)

After any change to `plugins/pi-subagents` — or to a new plugin you add — run:

```sh
~/Code/pi-config/pi-bolt/rebuild.sh
```

That is also what the shim's warning names, so a missed rebuild is one line of
output away from being obvious rather than a silent stale load.

**A failed rebuild does not block anything.** The usual cause is source broken
mid-edit, and refusing to start pi-bolt exactly when you want it to help you fix
that would be its own bug. The failure is printed and the previous (working) bundle
is used. `--check` is the mode with an exit code, if you ever want to gate on it.

### The hook: the `pi` shim, not `~/.zshrc`

This used to be a `pi()` function appended to `~/.zshrc`. It is not any more, and
that file now says so explicitly. Two reasons: it only ran in an interactive zsh,
so an update run by an agent through pi's bash tool skipped it entirely, and a
`.zshrc` that gets rewritten takes the hook with it (which is what happened —
`.zshrc` here has been hook-free since 2026-10-11).

The hook lives in the `pi` shim instead, which is the one place every route goes
through: `pi-swap.sh` writes it, `pi` is it in every shell, and a process tree
started by pi or Orca gets the same file on `PATH`. After `pi update` and
`pi compile` it runs `after-update.sh` — see [Keeping up to date](#keeping-up-to-date) —
and it still preserves the command's exit code, so a failed update stays failed.

A stale rebuild reports two lines rather than the builder's whole log:

```
pi-bolt bundles: rebuilding pi-bolt-web-access (source version 0.40.0 -> 0.41.0)…
pi-bolt bundles: rebuilt pi-bolt-web-access — built @nplez1/pi-bolt-web-access from pi-web-access@0.41.0
```

That pair is the real output of the first genuine `pi update --extensions` after
this was installed: it bumped pi-web-access 0.40.0 → 0.41.0, the hook noticed the
version change, and the bundle was rebuilt before the next launch.

## Keeping up to date

Three commands are supposed to be all a machine needs: `pi update`,
`pi update --extensions` and `pi compile`. Each moves something that nothing else
notices, and none of the three says a word about it, so `after-update.sh` (run by
the `pi` shim afterwards) reconciles them:

| What drifts | Why it drifts | Reconciled by |
|---|---|---|
| A vulnerable dependency | `pi update --extensions` re-resolves the extension tree; a release bump regenerates the managed release's `package.json`, dropping the `undici` override | `deps-audit.sh` — pins, then `npm audit fix` |
| A stale bundle | `pi update --extensions` can bump `pi-web-access`, and the prebuilt bundle wrapping it is a snapshot — pi-bolt then silently runs the old code | `rebuild.sh --if-stale` |
| The compile record | `pi compile --off` deletes `~/.pi-bolt/compile.json`, and a release bump can too; the compile set then silently falls back to *everything installed*, which dies on the one extension Bun refuses (top-level `await`) | re-runs `pi-bolt compile --exclude <compile-exclude.txt>` |

The third one is also fixed *before* it can fail: the shim adds
`--exclude $(compile-exclude.txt)` to a bare `pi compile`, merging it with any
`--exclude` the caller gave (a repeated `--exclude` replaces rather than adds), so
the build cannot hit the top-level `await` whether or not the record survived.
The first compile after `pi compile --off` therefore works instead of erroring.

```sh
$ pi update --extensions          # the two lines below are the automation talking
Updated packages
pi deps: .pi/agent/npm: pinned undici ^8.12.3
pi sync: recompiling (the compile record is missing)…
pi sync: compiled in: orca-prefill, orca-agent-status, …, pi-system-one
```

Everything is silent when there is nothing to do, so a healthy update prints
nothing beyond what `pi` itself says. Passed through untouched, because the caller
has said what they want: `pi update --models` (moves no packages),
`pi compile --off`, `--status`, `--only …` and `--no-exclude`.

`pi-bolt update` and `pi-real update` bypass the shim by definition. Run
`pi-bolt/after-update.sh` afterwards, or `install.sh`, which does the same work
plus the bundle rebuild.

```sh
pi-bolt/after-update.sh            # do what is needed, print what changed
pi-bolt/after-update.sh --check    # report and exit 1; change nothing
pi-bolt/after-update.sh --verbose  # print every verdict
pi-bolt/deps-audit.sh --check      # just the dependency half
```

## Dependencies: `npm audit`

Every package in `~/.pi/agent/npm` is an extension, so a vulnerable transitive
dependency there is this repo's to pin — no upstream will do it for us. On
2026-10-24 `npm audit` reported five (2 moderate, 3 high): `body-parser`,
`fast-uri`, `ip-address`, `undici` and `zod`, all reachable through
`pi-web-access@0.41.0`. Four moved within their own ranges with a plain
`npm audit fix` in that directory; nothing in the tree needed a major bump.

The fifth cannot be reached that way. `@earendil-works/pi-coding-agent` — Pi
itself, installed into the extensions project as a dependency of most extensions
— pins `undici` to **8.10.2 exactly**, which carries GHSA-4qv8-2p9j-2685
(EventSource parser DoS), GHSA-f72v-6w45-q472 (SRI bypass via non-lowercase
algorithm tokens) and GHSA-xjj6-f33q-929c (DoS on excessive content-encodings).
`npm audit fix` offers only `--force`, which would downgrade
`@tintinweb/pi-subagents` to 0.13.0 — a breaking change that fixes nothing
directly. The pin is what has to move, with an override in the extensions
project's `package.json`:

```json
"overrides": { "undici": "^8.12.3" }
```

A patch bump inside the same major, then `npm install --legacy-peer-deps` in
`~/.pi/agent/npm` (which also collapsed the nested copy into the hoisted one).
It sticks: `pi update --extensions` runs `npm install --prefix … --legacy-peer-deps`,
which preserves the field. **`npm audit` → 0 vulnerabilities** as of 2026-10-24.

None of that is a step anyone has to remember: `deps-audit.sh` owns it, and
[the `pi` shim runs it after every update](#keeping-up-to-date). `install.sh` runs
it too, and it re-asserts both trees — the managed release's `package.json` is
regenerated on every `pi update`, so the override has to be reapplied, not applied
once.

The **managed pi release** (`~/.pi/agent/install/releases/<version>`, what
`pi-real` runs) has the same pin and the same one real finding. Its lockfile root
`package.json` already carries an `overrides` block — `protobufjs` 7.6.6 — which is
regenerated by `pi update`, so `undici` went in beside it and `install.sh`
re-asserts both trees. The stale `1.2.0` release directory still reports the old
pin; nothing points at it (`install/current-version` is `1.3.0`) and it is only a
rollback slot, so it was left alone.

Worth knowing: `npm install` reported "removed 110 packages" the first time the
overrides were applied. Those were extraneous — present in `node_modules`, absent
from the lockfile — and no locked package changed, so the tree only got smaller.

## pi-bolt compile

`pi-bolt compile` builds installed extensions into the executable as machine code.
Three limits bite here (see
[PLUGINS.md](https://github.com/opensec-git/Pi-Bolt/blob/pi-bolt/docs/PLUGINS.md)):

- **Only `npm:` packages compile in.** Local checkouts are passed over with
  "only npm: packages can be compiled in (a git: checkout is resolved by Pi)", so
  `plugins/pi-subagents`, `plugins/pi-advisor-subagent` and `plugins/pi-todo`
  never can be. The three `pi-bolt-bundles/` are passed over for a different
  reason: they are Bun builds that load their real code from a `core.cjs`
  sibling, which a compiled executable has no file for.
- **A module with a top-level `await` is refused**, and it fails the whole build,
  not just that extension:
  `This require call is not allowed because the transitive dependency "…/package-juicesharp-rpiv-ask-user-question/index.ts" contains a top-level await`.
  That arrived in `@juicesharp/rpiv-ask-user-question` 2.15.0, which registers its
  i18n strings with `await import("@juicesharp/rpiv-i18n/loader")` so the SDK can
  stay an optional peer. Nothing to wait for — exclude it.
- **A module over 256 KB of bytecode is refused.** `pi-web-access`'s bundle needs
  372,946 bytes. This is why that package is not compiled in; the documented
  escape hatch `BUN_JSC_omitBytecodeFromStaticHeap=0` did **not** reach the
  compiler when set on `pi-bolt compile` — same error verbatim.

### The exclusion is what gets recorded, not the compile set

`pi-bolt compile` with no flags builds *every* installed extension, and `--only`
is **not** remembered — so the `--only` this repo used until 2026-10-24 did not
survive a bare `pi compile` or a `pi-bolt update`, both of which rebuilt the whole
set and died on the first extension the compiler refuses (loudly, at
`.pibolt-plugins/src/plugins.ts`). `--exclude` **is** recorded in
`~/.pi-bolt/compile.json`, and both of those read it, so the durable half is the
exclusion list: **`pi-bolt/compile-exclude.txt`**. Two callers apply it so that no
one has to remember a flag: `install.sh`, and the `pi` shim, which adds
`--exclude $(compile-exclude.txt)` to a bare `pi compile` (merging it with any
`--exclude` the caller passed, because a repeated `--exclude` replaces rather than
adds). That second one is what makes a bare `pi compile` work even when
`~/.pi-bolt/compile.json` has been deleted — which `pi compile --off` does.

That makes the compiled-in set "everything installed, minus that file", which as
of 2026-10-24 is ten: `orca-prefill`, `orca-agent-status`,
`pi-picker-patch-guard`, `nice-model-footer`, `model-manager`,
`orca-titlebar-spinner`, `deepseek-pricing`, `pi-codex-goal`,
`pi-smart-compaction`, `pi-system-one`. Excluded:
`juicesharp-rpiv-ask-user-question` (11 ms from its files instead).

The seven globals cost 0–1 ms each at run time, so compiling them buys nothing
measurable — it buys not having to re-pass a flag, and a fresh machine and a
release bump landing on the same set without anyone deciding. The cost is that
editing one (Orca rewrites `orca-agent-status.ts`) makes Pi load it from its files
with a "run `pi-bolt compile` again" warning until the next compile. That is the
intended behaviour, not an error. To go back to a hand-picked set, pass `--only`;
to compile the excluded one in as well, `--no-exclude` (which fails while it is
there).

A dropped record is what bit on 2026-10-24: `~/.pi-bolt/compile.json` did not exist
any more (the machine had moved from the `-jit` build and then to 1.0.2), so the
old `--only` interception was gone with it. `install.sh` re-asserts the exclude on
every run for exactly that reason.

`pi-system-one` was added 2026-10-18, pinned to `pi-system-one@1.3.4` in the
settings `packages` list; it registers the `system_one` judge tool (Jev through
Pi's native classifier or TypeSafe HTTP). Revert the whole thing with
`pi-bolt compile --off`: the replaced build is kept and `pi-bolt update --rollback`
restores it.

Compiling in works on the `-jit` build too, and keeps the JIT: verified 2026-10-19
by building to a throwaway `--out` directory and probing `bun:ffi`'s `dlopen` from
an extension — it succeeded (JIT on) for a build made from the `-jit` install, and
threw `bun:ffi requires the JIT` for one made from the JIT-less install. Note that
the release kit's `kit.json` sets `BUN_JSC_useJIT=0` in `env` for *both*, so that
key is not what decides the result; do not "fix" a compile by editing it.

### `import.meta.url` in compiled extensions — fixed upstream in 0.9.5

Compiled-in extensions used to lose any resource they resolved from their own
module URL. `pi-system-one` locates its bundled `skills/` and `prompts/` as
`join(dirname(fileURLToPath(import.meta.url)), "..", "skills")`, and bundling
resolves `import.meta.url` once, to the *output* file — so compiled in it named the
executable's virtual entry `file:///$bunfs/root/pi-bin`, the path collapsed to
`/$bunfs/skills`, and the `system-one` skill and `/judge` prompt were silently
missing while `/so` still answered.

`patch-kit.mjs` worked around that by pinning `import.meta.url` in every staged
script before bundling. **The workaround is gone: 0.9.5's kit does it itself**
(`pinImportMetaInCopy`, applied to every staged extension and to staged
dependencies), so the script was deleted on 2026-10-19 and nothing needs re-running
after `pi-bolt update` or `pi-bolt compile` any more. Its own `--check` is what says
so — against a 0.9.5 kit it reports "the kit's gen-plugin-manifest.mjs no longer
matches this patch (url import anchor missing) … drop this script if it does".
